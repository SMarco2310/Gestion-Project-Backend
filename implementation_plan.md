# Custom OAuth 2 Integration Plan (Client Mode)

Based on your clarification, your application (the one we are working on) will act as the **OAuth Client**, and your colleague's application will act as the **OAuth Server**. Users will be able to log into your application using their credentials from your colleague's app. 

To accomplish this while minimizing database changes and keeping your existing email/password system, we will use **Laravel Socialite** configured with a **Custom Provider** to talk to your colleague's server.

## User Review Required

> [!CAUTION]
> **Colleague's OAuth Server Requirements:**
> To implement this, your colleague's OAuth server MUST expose the standard OAuth2 endpoints. Please coordinate with them to ensure you have the following information:
> 1. **Client ID** and **Client Secret** (generated by their server for your application).
> 2. **Authorization URL**: The endpoint on their server where users go to approve the login (e.g., `https://their-app.com/oauth/authorize`).
> 3. **Token Token URL**: The API endpoint on their server where we exchange the authorization code for an access token (e.g., `https://their-app.com/oauth/token`).
> 4. **User Info URL**: The API endpoint on their server where we fetch the user's details (like email, name, ID) using the access token (e.g., `https://their-app.com/api/user`).

## Open Questions

1. **Password Nullability:** Since users from the other app won't have a local password in your database, we need to make the `password` field in the `users` table `nullable`. Is this acceptable?
2. **Account Linking:** If a user logs in via your colleague's app, but an account with that email already exists in your database (created via standard sign-up), should we automatically link the accounts and log them in, or return an error? (Usually, linking is preferred).

## Proposed Changes

---

### Backend (Laravel API)

We will use Laravel Socialite and build a custom driver for your colleague's server.

#### [NEW] `database/migrations/xxxx_xx_xx_xxxxxx_add_oauth_fields_to_users_table.php`
- Create a migration to update the existing `users` table.
- Add `provider_id` (string, nullable) to store the unique user ID from your colleague's server.
- Modify the `password` column to be `nullable()`.

#### [MODIFY] `app/Models/User.php`
- Add `provider_id` to the `$fillable` array.

#### [NEW] `app/Providers/CustomSocialiteServiceProvider.php`
- Extend Laravel Socialite to register a custom driver for your colleague's OAuth server.
- This provider will define the `getAuthUrl()`, `getTokenUrl()`, and `getUserByToken()` methods pointing to your colleague's endpoints.

#### [NEW] `app/Http/Controllers/OAuthController.php`
- **`redirect` method:** Redirects the user to your colleague's server for authentication.
- **`callback` method:** Handles the code returned by your colleague's server, fetches the user info, finds or creates the user in your `users` table, logs them in via Sanctum, and redirects back to the Nuxt frontend with the token.

#### [MODIFY] `routes/api.php`
- Add endpoints:
  - `GET /auth/custom/redirect`
  - `GET /auth/custom/callback`

#### [MODIFY] `.env` and `config/services.php`
- Add configuration for the custom OAuth server:
  - `CUSTOM_OAUTH_CLIENT_ID`
  - `CUSTOM_OAUTH_CLIENT_SECRET`
  - `CUSTOM_OAUTH_REDIRECT_URI`
  - `CUSTOM_OAUTH_SERVER_URL`

---

### Frontend (Nuxt Client)

#### [MODIFY] `client/app/pages/auth/login.vue` (and signup.vue)
- Add a "Login with [Colleague's App Name]" button to the login and signup forms.
- This button will navigate the user to the Laravel `/api/auth/custom/redirect` endpoint.

#### [NEW] `client/app/pages/auth/oauth-callback.vue`
- Create a new Nuxt page to handle the redirect from your backend after a successful login.
- It will extract the authentication token (passed via URL parameter or cookie by the backend), update the local authentication state (using your existing auth store/composables), and redirect the user to the dashboard.

## Verification Plan

### Automated Tests
- Integration tests can be tricky without the live server, so manual verification will be the primary method.

### Manual Verification
1. **Database:** Verify the migration runs successfully and `password` is nullable.
2. **Standard Auth:** Verify that the existing email/password sign-up and login still work flawlessly.
3. **OAuth Flow:** Click the new Login button, verify it redirects to your colleague's server. Log in there, approve the request, and ensure you are redirected back to the dashboard logged in as that user.
4. **Duplicate Email Handling:** Verify the behavior when an existing user tries to log in via the custom OAuth for the first time.
